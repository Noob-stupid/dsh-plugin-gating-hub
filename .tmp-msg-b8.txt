fix(git): 克隆报错带上"本次收到多少字节"（加法，B-⑧）

动机：真机 ghproxy 的失败是 **0 B/s**（一个字节都没传），而"慢但在传"的源只是需要更久。
只写"超时"两个字，用户（和面板）无法判断该换源还是该再等 —— 字节数是唯一的事实依据。
同一份事实也是 A-②"要不要用更长超时重试"的判据（0 B 不重试、>0 B 才重试）。

改法（加法，不动判据与流程）：
· summarizeCloneErrors：超时项写成 `…（超时，进程已结束；本次仅收到 0 B）` /
  `…（本次已收到 20480 B）`；没有 bytesReceived 字段时**不瞎编数字**（保持旧文案）。
· 非超时的失败消息也补上字节数：`<git stderr>（本次收到 N B）` / `git clone 退出码 N（本次收到 N B）`。
· 量法沿用 A-② 的 measureProgressBytes：优先 `.git/objects`（git 边下边写 pack 的进度所在），
  没有它才退化成量整棵目标目录。

验收：tests/test-clone-bytes.mjs（CI 硬门槛，全部离线）
· 0 B / 20480 B / 字段缺失 三种文案各自的准确措辞
· 量法：只有 .git/objects → 只算它（4096 B，不被仓库里其它 99999 B 干扰）；没有它 → 量整棵树
· 端到端（真跑 gitCloneRepo，假 git 永不退出）：0 进度 → "本次仅收到 0 B" + 不做长超时重试；
  8192 B → "本次已收到 8192 B" + 触发同源更长超时重试
